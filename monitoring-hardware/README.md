# Hardware monitoring

Prometheus reads the hardware through three exporters. The alerts go to
Discord through the existing Alertmanager. The **Hardware** dashboard in
Grafana (folder Hardware, uid `hardware`) shows all of it, and its Storage
row shows storage health (below).

This replaced Zabbix on 2026-10-24.

## What is monitored

| Device | Address | Exporter, job | What it gives |
|---|---|---|---|
| jd-proxmox-02's BMC (Lenovo XCC) | 10.0.50.240 | ipmi_exporter, `ipmi` | Every sensor with its state (temperatures, fans, voltages, power, memory, processors, drive bays, PCIe errors), DCMI power, chassis state, event log |
| linds-proxmox-01's iDRAC8 | 192.168.6.240 | snmp_exporter, `snmp`, modules `system,dell_health` | Component status (power supplies, fans, temperatures, voltages, memory, processors, batteries, intrusion), readings, power |
| jd-proxmox-02, linds-proxmox-01 (Proxmox API) | 10.0.50.246, 192.168.6.205 | prometheus-pve-exporter, `pve` | Each host, each guest (state, CPU, memory, disk and network I/O), each storage |
| linds-truenas-01 | 10.3.1.50 | snmp_exporter, `snmp`, `system,if_mib,ucd_la_table,ucd_memory,truenas` | Pool health and space, pool I/O, ARC, interfaces, load, memory |
| linds-switch-01 (OfficeConnect 1920S) | 192.168.6.210 | snmp_exporter, `snmp`, `system,if_mib` | Ports: link, speed, traffic, errors |
| linds-vyos-01 | 192.168.6.1 | snmp_exporter, `snmp`, `system,if_mib,ucd_la_table,ucd_memory` | Interfaces, load, memory. Remove at the cutover to linds-router-01. |

Not here, because other jobs already do it:

- Disks, ZFS pools, the PERC and the LVM thin pools of both hosts:
  `base/monitoring/proxmox-storage-health.yaml` (LINDS-Ansible role
  `storage_health`). Its job and alerts stay there; the dashboard's Storage
  row reads them. The row's status tiles show the storage alerts that are
  firing, so they agree with Discord.
- jd-router-01: `base/monitoring/router-metrics.yaml`.
- The Talos nodes: kube-prometheus-stack.

## Files

| File | What it is |
|---|---|
| `snmp-exporter.yaml`, `ipmi-exporter.yaml`, `pve-exporter.yaml` | The exporters. snmp_exporter prefers a LINDS node, the other two a JD node: each one is near what it reads. |
| `snmp/truenas.yml` | The TrueNAS module, written by hand from TRUENAS-MIB. |
| `snmp/dell-health.yml` | The iDRAC module. Generated by `snmp/build-dell-health.py`; do not edit it by hand. |
| `external-secrets.yaml` | The config files of the IPMI and Proxmox exporters, made from Vault. |
| `scrape-configs.yaml` | The targets: one per device, with its name (`instance`), `site` and modules. |
| `rules.yaml`, `tests/rules.test.yaml` | The alerts and their unit tests. |
| `dashboard.py` | Makes `dashboard.yaml`. Edit it, then run `python3 monitoring-hardware/dashboard.py > monitoring-hardware/dashboard.yaml`. |
| `dashboard.yaml` | The Grafana dashboard. Generated by `dashboard.py`; do not edit it by hand. |

## Alerts

| Alert | Severity | When |
|---|---|---|
| `HardwareSensorNotOk` | warning or critical | A BMC sensor or iDRAC component is past its threshold for 10 minutes. Labels `sensor` and `kind` name it. |
| `HardwareBmcUnreachable` | warning | The XCC does not answer IPMI for 15 minutes. |
| `HardwareEventLogged` | info, a notice | The XCC's event log has a new entry. |
| `HardwareEventLogNearlyFull` | warning | Less than 1 KiB is left in the XCC's event log. |
| `HardwareHostRestarted` | info, a notice | A Proxmox host booted in the last 15 minutes. |
| `ProxmoxGuestStopped` | info, a notice | A guest that ran 30 minutes ago is stopped. |
| `StorageProxmoxLocalNearlyFull` | warning | A directory storage (the host's root file system) is over 90% full. |
| `StorageTrueNasPoolNotOnline` | critical | A TrueNAS pool is not ONLINE. |
| `StorageTrueNasPoolNearlyFull` | warning | A TrueNAS pool is over 85% full. |
| `NetworkInterfaceErrors` | warning | An Ethernet interface has more than 100 damaged frames in an hour. |

A device that does not answer is `PrometheusTargetDown`
(`base/monitoring/alerts.yaml`).

`base/monitoring/alertmanager-config.yaml` routes them:

- The three notices go to the `discord-notices` receiver. It sends no
  "resolved" message, because a notice clears by itself.
- `Storage*` alerts repeat once a day.
- While `RouterTunnelDown` fires for the LINDS tunnel, alerts with
  `site="linds"` are held back.

Test the rules after a change:

```bash
yq '.spec' monitoring-hardware/rules.yaml > /tmp/hardware.rules.yaml
promtool check rules /tmp/hardware.rules.yaml
promtool test rules monitoring-hardware/tests/rules.test.yaml
```

## Credentials

One Vault entry, `linds-keyvault/hardware-monitoring`:

| Key | What it is |
|---|---|
| `jd_proxmox_02_bmc_password` | The XCC password of the user `USERID` |
| `jd_proxmox_02_pve_token` | The secret of the API token `prometheus@pve!pve-exporter` on jd-proxmox-02 |
| `linds_proxmox_01_pve_token` | The same on linds-proxmox-01 |

To change a value, run this, then force-sync the ExternalSecret (its
`refreshPolicy` is `OnChange`, so a Vault edit alone does nothing):

```bash
kubectl -n vault exec -i vault-0 -- sh -c 'read -r VAULT_TOKEN; export VAULT_TOKEN;
  vault kv patch -mount=linds-keyvault hardware-monitoring jd_proxmox_02_bmc_password=-'
kubectl -n monitoring annotate externalsecret ipmi-exporter-config force-sync=$(date +%s) --overwrite
```

### Proxmox

The exporter logs in as `prometheus@pve`. That user has only the role
`PVEAuditor` on `/`, so it can read and cannot change anything. Each host has
its own user and token, made with these commands (run on the host):

```bash
pveum user add prometheus@pve --comment "Prometheus pve-exporter, read-only (PVEAuditor)"
pveum acl modify / --users prometheus@pve --roles PVEAuditor
pveum user token add prometheus@pve pve-exporter --privsep 0 --output-format json
```

The last command shows the token secret one time only. Put it in Vault.

Two things do not work as they should:

- **No onboot flag.** The exporter runs with `--no-collector.config`.
  On Proxmox VE 9.2 (pve-container 6.1.14), a user without
  `VM.Config.Options` cannot read the configuration of a container that has
  environment variables. jd-s3-01 (LXC 107) has them. The API gives 403 and
  does not leave out the restricted key, so the whole jd-proxmox-02 scrape
  fails. The cause is `PVE::LXC::delete_read_restricted_options`: it calls
  `check_vm_perm(..., [$priv], 1)`, and that `1` is the `$any` argument, not
  `$noerr`. Without the onboot flag, `ProxmoxGuestStopped` can only say that
  a guest stopped. It cannot say that a guest should run. When Proxmox fixes
  this, remove the flag and change the alert to use `pve_onboot_status`.
- **TLS is not verified** (`verify_ssl: false`). Each host's API certificate
  is signed by its own Proxmox CA. That CA certificate has no keyUsage
  extension, and Python 3.13 and later refuse it, even when the CA is given.

### XCC

The IPMI login is the XCC's `USERID` account, with privilege `user`: it reads
sensors and the event log only. The XCC's SNMPv3 agent is not used.

## Add a device

- **An SNMP device:** add a target to the `snmp` ScrapeConfig, with its
  `instance`, `site`, `device`, `__param_module` and `__param_auth`. The
  modules in the image's own
  [snmp.yml](https://github.com/prometheus/snmp_exporter/blob/main/snmp.yml)
  cover most devices (`if_mib`, `system`, `ucd_*`, `hrStorage`, `synology`,
  `ubiquiti_unifi`, and others). For a device with no module, write one in
  `snmp/`, add it to `configMapGenerator` in `kustomization.yaml` and to the
  exporter's `--config.file` arguments.
- **A BMC over IPMI:** add a module to the `ipmi.yml` template in
  `external-secrets.yaml`, the password to Vault, and a target to the `ipmi`
  ScrapeConfig.
- **A Proxmox host:** make the user and token, add a module to `pve.yml` in
  `external-secrets.yaml`, the token to Vault, and a target to the `pve`
  ScrapeConfig.

To see what a device returns before you add it:

```bash
kubectl get --raw '/api/v1/namespaces/monitoring/services/http:snmp-exporter:9116/proxy/snmp?target=10.3.1.50&module=system,truenas&auth=public_v2'
```

## Upgrade snmp_exporter

`snmp/dell-health.yml` is made from the `dell` module of the image's
`snmp.yml`. After a version change, run `snmp/build-dell-health.py` again
with the new version (its docstring has the command). If the output changes,
commit it with the image tag.

## Limits

- linds-truenas-01 is a VM on linds-proxmox-01 (qemu/103). Its disks are
  virtual: the drives under them are storage health's (the PERC and SMART on
  linds-proxmox-01). TrueNAS 25.10 has no disk temperatures over SNMP in any
  case (`hddTempTable` answers "No Such Object").
- The switch's own MIB has one PSU state and no fan or temperature readings,
  so only its interfaces are monitored.
- The UniFi switches and access points at JD are not monitored. SNMP is off
  on them, and the UniFi console must turn it on.
