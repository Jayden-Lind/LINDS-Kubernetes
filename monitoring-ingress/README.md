# Ingress traffic

The **Ingress traffic** dashboard in Grafana (folder Network, uid
`ingress-traffic`) shows the requests through the two ingress controllers:
for each site, the request volume, the errors, the latency, the clients, and
the refusals of the client-certificate gate. Three alerts go to Discord.

| Controller | Namespace | Serves | Client address that nginx sees |
|---|---|---|---|
| `nginx` | nginx-ingress | The LAN, the VPN and the pods. Not on the internet. | The real address: a LAN device, the VPN address of the router, or a pod |
| `nginx-mtls` | nginx-ingress-mtls | The internet: the router forwards WAN port 443 to it. It requires a client certificate. | The real address of the client on the internet |

nginx sees the real address of an internet client. The router forwards port
443 with DNAT only (no NAT of the source), the Service has
`externalTrafficPolicy: Local`, and Cloudflare serves DNS only (it does not
proxy). So no forwarded-address header is needed, and none can be trusted:
a client can send any `X-Forwarded-For`. The log keeps that header in `xff`,
for information only. `real-ip` is not configured on either controller.

The sites on the internet are the hosts of the `nginx-mtls` Ingresses (the
mTLS mirrors). The dashboard lists them in "Sites on the internet".

## Files

| File | What it is |
|---|---|
| `dashboard.py` | Makes `dashboard.yaml`. Edit it, then run `python3 monitoring-ingress/dashboard.py > monitoring-ingress/dashboard.yaml`. |
| `dashboard.yaml` | The Grafana dashboard. Generated by `dashboard.py`; do not edit it by hand. |
| `alerts.yaml` | The three alerts: rules for Loki's ruler (label `loki_rule`). |

The access-log format is in `applications/nginx-ingress.yaml` and
`applications/nginx-ingress-mtls.yaml` (ConfigMap keys `log-format` and
`log-format-escaping`).

## The access log

Each request is one line of JSON. The panels parse it at query time with
`| json`. Alloy adds no labels for it.

| Key | nginx variable | Why |
|---|---|---|
| `t` | `$time_iso8601` | The time, for a line read outside Loki |
| `ip` | `$remote_addr` | The client address |
| `xff` | `$http_x_forwarded_for` | What the client claims as its address. Not trusted. |
| `host` | `$host` | The host that the client asked for |
| `sn` | `$server_name` | The server that answered: the Ingress host, or `_` for the default server (no Ingress has the host). The dashboard and the alerts group by this. |
| `m` | `$request_method` | The method |
| `path` | `$request_uri_no_args` | The path, without the query string |
| `proto` | `$server_protocol` | HTTP/1.1, HTTP/2.0 |
| `s` | `$status` | The status that the client got |
| `bytes` | `$body_bytes_sent` | The size of the answer body |
| `rt` | `$request_time` | Seconds from the first byte of the request to the last byte of the answer |
| `up` | `$upstream_addr` | The pod that answered. `unix:...nginx-502-server.sock` means that the Service had no ready pod. |
| `ups` | `$upstream_status` | The status that the app gave |
| `urt` | `$upstream_response_time` | Seconds until the app's whole answer |
| `uht` | `$upstream_header_time` | Seconds until the app's first byte. This is the latency of the app. |
| `ing` | `$resource_namespace/$resource_name` | The Ingress. `/` when nginx refused the request before it matched one. |
| `svc` | `$service` | The Service |
| `tls` | `$ssl_protocol` | TLSv1.3, TLSv1.2, or empty for plain HTTP |
| `cipher` | `$ssl_cipher` | The cipher |
| `ua` | `$http_user_agent` | The user agent |
| `origin` | `$http_origin` | The site that sent a cross-site request (empty for most requests) |
| `cv` | `$ssl_client_verify` | nginx-mtls only: `SUCCESS`, `NONE` (no certificate) or `FAILED:<reason>` |
| `dn` | `$ssl_client_s_dn` | nginx-mtls only: the subject of the client certificate |
| `allowed` | `$mtls_client_allowed` | nginx-mtls only: 1 if the subject is in the allow map, else 0 |

What is not logged, and why:

- **The query string.** Query strings here can hold OAuth codes, state
  values and tokens (for example the Home Assistant login callback and its
  image URLs).
- **The referer.** It is the whole URL of the page before, with its query
  string. `origin` shows a cross-site request without the path.

NOTE: `$request_uri_no_args` comes from the controller's main template
(nginx.tmpl), not from nginx. The controller uses it for VirtualServer
rewrites. After an upgrade of the nginx-ingress chart, make sure that
`nginx_ingress_controller_nginx_last_reload_status` is 1. If nginx cannot
load the format, the reload fails and `NginxConfigReloadError` fires.

### Volume

Measured on 30 days of real lines (2026-10-29 to 2026-11-28), converted to
this format: an access line is 474 bytes on nginx (223 before) and 510 bytes
on nginx-mtls (201 before). That is about 2.2 MB a day on nginx and 0.3 MB on
nginx-mtls, about 1.3 MB a day more than before. Loki takes about 350 MB a
day in total.

The access log is not most of these streams. On 2026-11-27/28 it was 1.1 MB
of 3.6 MB on nginx. The rest is nginx's reload notices ("gracefully shutting
down", "exiting" and "exit" from each worker process at each reload) and the
controller's own log. The reloads come in bursts when many pods change, for
example after node restarts.

## Dashboard

| Section | What it shows |
|---|---|
| Top | Requests per second, 5xx share, 4xx share, request time p50 and p95, client addresses, for each controller. Sites ranked by 5xx and by latency. |
| Sites | Requests by status class, server errors by kind (no ready pod, 502, 503, 504, other), request time, time to first byte by site, paths with the most 5xx, paths with slow answers. The Site variable selects the sites. |
| Clients | Internet and internal clients, top clients, clients with the most 4xx, user agents, unknown hosts (default server), scanner requests and scanner clients. |
| Logins and client certificates | 401 and 403 by site, the reasons that nginx-mtls refused requests, requests by client certificate, and the tripwire count (must be 0). |
| Requests | The newest 500 requests, with the variables as filters. |
| From the controllers' metrics | The Prometheus metrics of the controllers. They do not need the JSON log. |

Variables: Controller, Site (the Ingress hosts), Source (internet or
internal), Client (a regular expression), and for "Recent requests" only:
Status and Path contains.

CAUTION: Loki refuses a query that makes more than 2000 series. A scan asks
for thousands of different paths, so no panel groups 4xx by path.

## Alerts

All three are rules for Loki's ruler, in `alerts.yaml`.

| Alert | When | Severity, route |
|---|---|---|
| `IngressSiteServerErrors` | A site (`sn`) answered more than 20% of its requests with 5xx in 30 minutes, with at least 10 of them, for 15 minutes | warning, Discord with "resolved" |
| `IngressAuthFailureBurst` | One client got 20 or more answers 401 or 403 from one site in 10 minutes | warning, discord-security |
| `IngressMTLSPassedWithoutCertificate` | nginx-mtls served a request (2xx or 101) without a verified client certificate whose subject is in the allow map | critical, discord-security |

How often they would have fired in 30 days (2026-10-29 to 2026-11-28),
measured on the real lines. The old format had no host, so the site is
guessed from the path:

- `IngressSiteServerErrors`: 9 times. 7 for vault.linds.com.au: Vault
  answered every login of the External Secrets Operator with 503 for 45
  minutes to 26 hours (one outage made two alerts). 1 for photos.linds.com.au
  (Immich, 502) and 1 for home.linds.com.au (502).
- `IngressAuthFailureBurst`: 0 times. The most from one client in 10
  minutes was 4 (a browser with an expired Grafana session).
- `IngressMTLSPassedWithoutCertificate`: cannot be measured, because the old
  format had no certificate result. It must never fire.

`NginxHighErrorRate` (base/monitoring/alerts.yaml) reads the controllers'
latency histogram: only requests that reached a pod, 5% over 5 minutes, no
floor. It does not see a site with no ready pod. In the 14 days that
Prometheus keeps, it fired 5 times, all for Vault, each for 0 to 8 minutes,
and it did not fire for the Vault outage of 2026-11-27.

## Test a change

1. Make the dashboard again and check it builds:

   ```bash
   python3 monitoring-ingress/dashboard.py > monitoring-ingress/dashboard.yaml
   kubectl kustomize monitoring-ingress/
   ```

2. Run a changed query in Grafana Explore (data source Loki) first. Use a
   time range with traffic.
3. To test a rule without an alert, run its expression in Explore. A value
   means that the rule fires.
4. After a change to the log format, check each new variable in the nginx
   documentation. An unknown variable makes every reload fail.
